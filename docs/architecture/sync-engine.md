# Sync Engine

The Sync Engine executes `ApprovedMapping`s between two `PROVIDER`-role apps on an ongoing basis, keeping their data in sync. It is one of the two consumers of approved mapping data (the other being the [Adapter/Gateway Engine](adapter-engine.md)) — where the adapter resolves requests on demand, the Sync Engine pushes proactively.

## Transports: webhook push and polling pull

Each `SyncRule` (one per mapped resource pair of an `ApprovedMapping` between two peer apps, see [data-model.md](data-model.md)) runs over one or both transports, chosen per app based on its declared `capabilities`:

- **Webhook push** — used when the source app declares `supportsWebhooks`. The app notifies the mediator's Webhook Receiver of changes; the mediator propagates them near-real-time. How the subscription comes to exist depends on `capabilities.webhookSetup` (see [data-model.md](data-model.md)): under `managed`, the source app's API exposes subscription management and the mediator creates/deletes the subscription itself when the `SyncRule` is enabled/disabled, storing the handle in `webhookSubscriptionRef`; under `manual`, the registration UI shows the per-app webhook URL and signing secret for a human to configure in the source app, and the webhook transport is not considered live until the first correctly-signed webhook arrives — the polling transport, when available, covers the gap in the meantime. Two further payload realities are declared per app rather than assumed (see [data-model.md](data-model.md)): `webhookPayload = thin` — the webhook carries only the changed record's id — makes the Receiver fetch the record back from the source before the pipeline runs (the fetch reads *current* state, possibly already containing newer edits, which is safe precisely because sync is state-convergent); and `webhookVerification = none` — the app cannot sign its webhooks — demotes the webhook to a **fetch trigger**: its content is never fed to the pipeline, it only causes an immediate authenticated poll of the source, rate-limited per app (see [security.md](security.md)).
- **Polling pull** — used when the source app only declares `supportsPolling` (or as a supplementary safety net alongside webhooks, to catch missed events). The Poller periodically calls the source app on `SyncRule.pollIntervalOverride` or `RegisteredApp.defaultPollInterval`.

Both transports funnel into the same shared pipeline: **Identity Resolution → Loop Prevention → Conflict Detection → Transformation Executor → Outbound Call Executor**, so mapping semantics are identical regardless of how a change was detected. Identity Resolution runs first because everything downstream operates on the record's `RecordLink` — the echo check compares against link-scoped `SyncFieldState` — so only the short-TTL recently-written cache, keyed by native id, can short-circuit ahead of it (see *Loop prevention* below).

## Webhook push pipeline

1. Source app sends a webhook to the mediator's per-app webhook URL.
2. Webhook Receiver verifies the request signature using the app's `webhookSecret` credential (see [security.md](security.md)). Unsigned/invalid requests are rejected before reaching the pipeline.
3. Receiver resolves the active `SyncRule`(s) for `(sourceApp, resource)`. For a `webhookPayload = thin` or `webhookVerification = none` source, the changed record is first fetched back from the source over the authenticated outbound channel (see *Transports* above). The short-TTL "recently written by mediator" cache may short-circuit an obvious echo here, as a fast path.
4. Identity Resolution classifies the change as create/update/delete and resolves its `RecordLink` — establishing one first (by identity-key match against the target) for a record the mediator has never seen. See *Identity correlation* and *Change types* below.
5. Loop Prevention checks whether this change is an echo of the mediator's own last write: the incoming values are compared field-by-field against the source side's reconciled baselines in the link's `SyncFieldState` (see below). If so, record `skipped-loop` and stop.
6. Conflict Detection checks whether the *target* side has drifted from its own reconciled baseline since the last sync; a drift resolves per the conflict policy — auto-resolve and record `conflict`, or park the field for manual resolution (see *Conflict handling* below).
7. Transformation Executor applies the `ApprovedMapping`'s `FieldMapping`s (rename/coerce/aggregate/expression) to produce the target payload.
8. Outbound Call Executor obtains the target app's credential via `CredentialStore.withCredential` and calls the target operation selected by the change's action from the mapping's `OperationMapping`s (see [data-model.md](data-model.md)), tagged with a deterministic `idempotencyKey`. For a create, the target's newly assigned native id is captured from the response and persisted on the `RecordLink`.
9. Result recorded as a `SyncEvent`; the "recently written by mediator" cache is updated for the target app's resource.

Full step-by-step walkthrough with sequence diagram: [flows/sync-webhook-push.md](../flows/sync-webhook-push.md).

## Polling pull pipeline

1. Scheduler wakes a `SyncRule` on its configured interval.
2. Poller calls the source operation pinned by `SyncRule.pollOperationRef` (see [data-model.md](data-model.md)): the delta-query operation with the stored `cursor` when the app declares `capabilities.supportsDeltaQuery`, otherwise the collection read — paged to exhaustion via the operation's IR-declared pagination parameters — diffing the result against the last-seen snapshot by content hash. Deletions are only ever inferred from a **complete** full fetch — if any page fails, the run aborts rather than misreading missing records as deletions (see *Change types* below).
3. Each changed record goes through the same Identity Resolution → Loop Prevention → Conflict Detection → Transformation → Outbound Call pipeline as webhook push.
4. `SyncRule.cursor` and `lastRunAt` are advanced; a `SyncEvent` is recorded per changed record.

Full step-by-step walkthrough with sequence diagram: [flows/sync-polling-pull.md](../flows/sync-polling-pull.md).

## Identity correlation: RecordLink

Two independently-owned apps assign their own primary ids to the same logical record — nothing guarantees `customer 123` in App A is `cust_9f3` in App B. Every stateful sync behavior (routing an update to the right target record, conflict detection, delete propagation) therefore runs over an explicit, persisted id pairing: the `RecordLink` (see [data-model.md](data-model.md)), scoped to the unordered app pair and shared by both directions of a bidirectional pair, exactly like `SyncFieldState` (which is keyed by it).

A link is established one of three ways:

1. **Create propagation** — the pipeline creates the record in the target and captures the target's newly assigned native id from the create response, writing the `RecordLink` in the same step. This is also what makes the target's own "new record" event recognizable as an echo (see loop prevention below).
2. **Identity-key match** — during initial backfill, or in steady state when a change arrives for a source record with no link yet: the target is looked up by the mapping's confirmed identity `FieldMapping` (`isIdentityKey`, see [data-model.md](data-model.md)) — the business-level key (email, SKU, order number, …) whose values are expected to identify the same record on both sides. A lookup that matches **more than one** target record never picks one silently: the event is recorded as `failure` with the candidate ids in `details` and surfaced for manual linking.
3. **Manual** — the UI supports explicit linking/unlinking for records an identity key cannot disambiguate.

**How an identity-key lookup executes.** Matching needs the *target* queryable by the identity field's value — which not every REST API offers, so the mechanism is confirmed per resource pair rather than assumed. Preferred: a **filtered read** — the confirmed filter parameter on the target's collection read operation (`FieldMapping.targetLookupParamRef`, suggested by the Mapping Engine and reviewed alongside the identity key itself, see [data-model.md](data-model.md)). Fallback: **fetch-and-match** — a complete fetch of the target resource with in-memory comparison, available only when the target is enumerable (the same complete-fetch capability polling and backfill rely on). A resource pair with *neither* path cannot match records at all: its backfill can only be explicitly skipped, match-first is unavailable (creates go straight to create, risking duplicates for pre-existing data), and links can only be established by create-propagation or manually — the enablement UI states exactly this degradation before the rule can be turned on.

Because a wrong identity key makes the engine silently merge unrelated records — its worst possible failure mode — the identity `FieldMapping` is proposed by the Mapping Engine (`identityCandidate`, see [mapping-engine.md](mapping-engine.md)) but only ever set by explicit reviewer confirmation, and a `SyncRule` cannot be enabled without exactly one confirmed identity key per mapped resource pair (see [flows/mapping-review-and-approval.md](../flows/mapping-review-and-approval.md)).

## Change types: create, update, delete

A detected change carries an action, and "calls the mapped operation" always means *the target operation whose `OperationMapping.action` matches that action* (see [data-model.md](data-model.md)). Detection per transport:

- **Webhook** — the event-type field, when the source app's webhook payloads declare one; otherwise inferred from `RecordLink` state (no link and no identity match → create; link exists → update).
- **Delta query** — deletions only when the API explicitly reports deleted records; a delta API that doesn't report deletions cannot drive delete detection on its own.
- **Full-fetch diff** — a record present in the last snapshot but absent from a **complete** fetch is a delete candidate. This inference is only valid when every page of the fetch succeeded; a truncated or partially failed fetch aborts the run rather than misreading missing pages as mass deletion.

Per action:

- **Create** — before creating, the pipeline first attempts an identity-key match: the record may already exist in the target, created there independently or predating the sync. A match links the records and downgrades the change to an update; no match calls the `action = create` operation, captures the new target id from the response, and writes the `RecordLink`. Create propagation requires an approved `action = create` `OperationMapping` on the target side; a rule without one records observed creates as `skipped-policy` — visible, never silent — the same opt-in shape as delete propagation below.
- **Update** — routed to the target's native id via the `RecordLink`; a record with no link takes the same match-first path as a create.
- **Delete** — governed by `SyncRule.deletePropagation`, default `ignore`: deletion is the one destructive thing the mediator can do to an app, so propagation is opt-in per rule. Under `propagate`, the `action = delete` operation is called via the link, and the `RecordLink` is **tombstoned** (not deleted) with reason `propagated-delete`: the tombstone is what recognizes the other side's delete echo and prevents a slower poll cycle from resurrecting the record (see loop prevention below). Under `ignore`, the deletion is recorded as `SyncEvent.status = skipped-policy` — visible in the audit log and the graph's activity metadata, never silently dropped — **and the link is still tombstoned**, with reason `observed-delete`: one side of the pair no longer exists, so later changes to the surviving record are recorded `skipped-policy` (counterpart deleted) and surfaced, rather than misrouted at a deleted record or misread as needing a re-create. The surviving record stays unmanaged until it is re-linked manually or matched afresh by a genuine re-create on the deleted side, which arrives with a new native id and establishes a fresh link through the normal create path.

## Initial backfill

Enabling a `SyncRule` between two apps that already hold data raises a question steady-state sync never answers: what about the records that exist *now*? Each rule therefore starts with a one-time backfill run — tracked as `SyncRule.backfillStatus`, see [data-model.md](data-model.md) — before its transports go live. Skipping it is an explicit choice (`skipped`), not a default.

1. The Poller does a complete fetch of the source's mapped resource (the rule's `pollOperationRef` collection read, paged to exhaustion). Backfill therefore needs an *enumerable source*: for a webhook-only app that offers no way to list the resource, backfill can only be explicitly `skipped`, and pre-existing overlap links up gradually via steady-state identity matches or manual linking. Matching likewise needs an identity lookup path on the *target* (see *Identity correlation* above); with neither lookup path, backfill can link nothing — the enablement UI says so.
2. Each record is resolved against existing `RecordLink`s, then by identity-key match; matches produce links.
3. What happens beyond linking is `SyncRule.backfillMode`:
   - **`link-only` (default)** — links are written and `SyncFieldState` baselines are seeded — per side, from each side's own current stored value (see [data-model.md](data-model.md)) — but **nothing is written to either app**. Two sides *agree* when applying the rule's transform to the source value reproduces the target's stored value: agreement is only well-defined in the target's representation, since comparing raw values across a transform is meaningless. Fields whose two sides disagree get no baseline (there is no last-reconciled value to record) and are reported in the backfill summary; the first subsequent change to such a field is a conflict by construction and resolves per the normal conflict policy below.
   - **`push`** — the source is declared the initial source of truth for this direction: mapped field values are pushed to matched target records, and unmatched source records are created in the target — all through the normal pipeline (loop-prevention tagging, idempotency keys, audit). On a bidirectional pair, at most one of the two rules may use `push`; pushing both directions is a contradiction.
4. Backfill executions are ordinary `SyncEvent`s (`type = backfill-run`), and changes arriving over webhook mid-backfill queue behind it in the per-record ordering queue (see *Ordering and consistency* below) rather than racing it.

The two rules of a bidirectional pair share links and field state, so whichever backfills first does the bulk of the matching. The second direction's backfill still enumerates *its* source's records — records existing only in that app were never seen by the first run — but finds the overlap already linked.

## Loop prevention

Bidirectional sync — two paired one-way `ApprovedMapping`s / `SyncRule`s, see [data-model.md](data-model.md) — creates a real risk: App A changes → synced to App B by the A→B `SyncRule` → App B's own webhook/poll detects that change → the B→A `SyncRule` syncs it back to App A → infinite ping-pong.

Prevention mechanism — durable state is authoritative, the cache is only a fast path:

- **Authoritative check (no TTL):** an incoming change from side X is compared field-by-field against **side X's own reconciled baseline** (`SyncFieldState.lastSyncedHashA/B`, stored per side in each side's canonical representation — see [data-model.md](data-model.md)). If every mapped field matches that side's last-reconciled state, the change carries nothing the mediator doesn't already know — it is the echo of the mediator's own write (or a no-op) and is recorded as `SyncEvent.status = skipped-loop`. An echo always arrives from the side that was last written, so this comparison is always same-representation — never across the transform. Because this state is durable, echo detection does not depend on any cache lifetime: a polling source whose next poll runs hours after the mediator's write is handled identically to a webhook that echoes within seconds. (The check needs the record's `RecordLink` — `SyncFieldState` is keyed by it — which is why Identity Resolution runs *before* Loop Prevention in the pipeline; only the cache fast path below runs ahead of it.)
- **Fast path:** a short-TTL "recently written by mediator" cache per `(appId, resourceId)` short-circuits the common case before field-level comparison, and mediator-originated writes are additionally tagged via a passthrough header/field where the target API supports write metadata. Both are optimizations — correctness never depends on the cache TTL or on the target supporting tags.
- **Canonical-form capture:** target apps may normalize written values (trimming, date reformatting, server-side defaults), which would defeat a naive comparison against what the mediator *sent*. The written side's baseline is therefore recorded from the target's **stored representation** — taken from the write response body when the API returns the updated resource (the common REST case), or via a follow-up read of the written record when it doesn't — while the source side's baseline is the observed source value the write was computed from. The echo then matches exactly instead of ping-ponging over formatting differences.

Two cases content matching cannot cover are handled via `RecordLink` state instead:

- **Create echoes** — when the mediator creates a record in the target, the `RecordLink` written at propagation time (carrying the target's new native id) is what identifies the target's subsequent "new record" webhook/poll hit as the mediator's own create rather than a genuine new record.
- **Delete echoes** — a deletion has no content to hash; the tombstoned `RecordLink` is the marker. An observed deletion of a record whose link the mediator tombstoned with reason `propagated-delete` is the mediator's own deletion coming back, recorded `skipped-loop` (an `observed-delete` tombstone marks a severed pair instead — no echo is expected, see *Change types* above). Either tombstone also prevents *resurrection*: a slower poll cycle on the other side, still seeing the record in an old snapshot diff, must not re-create what was just deleted.

## Idempotency

Every outbound write carries a deterministic `idempotencyKey` — a hash of the mapping id, the **source record's native id** (not the `RecordLink`: a create has no link until its response is captured, and the source native id is exactly what two deliveries of the same change share), the resulting payload, **and the prior reconciled state the write was computed from** — the target-side `lastSyncedHash`es of the mapped fields at transformation time, or a distinguished *none* marker for a first write that establishes state. Including the prior state is what distinguishes a genuine value revert from a duplicate delivery: in A → X → Y → X, the third write starts from reconciled state Y while the first started from the initial state, so their keys differ — a payload-only key would wrongly deduplicate the revert as a "repeat" of the first write. A true duplicate delivery (webhook retry, overlapping poll) has the same payload *and* the same prior state, and is deduplicated.

Before executing, the Outbound Call Executor checks `SyncEvent` history for the key within a **bounded lookback window** (e.g. the last N events per record or a configured retention period — never unbounded history). The key is also passed through to the target API's own idempotency-key mechanism when it has one.

## Write failures: retry and dead-letter

A failed outbound write (5xx, timeout, network error) is retried with exponential backoff inside its per-record ordering queue (see *Ordering and consistency* below), up to a bounded attempt ceiling. At the ceiling the event is **parked**: recorded as `SyncEvent.status = failure` with a dead-letter marker, surfaced in the UI, and alerted (see [observability.md](observability.md)) — and the queue moves on. A permanently failing record must not block other records, nor later changes to the same record.

Skipping ahead is safe because sync is **state-convergent, not event-sourced**: each execution carries the record's current state, so any later successful sync of the same record supersedes the parked failure entirely. Manual replay of a parked event is only needed when no later change comes along; the replay action re-runs the standard pipeline (including loop prevention and conflict detection against current state) rather than blindly re-issuing the stale payload.

## Conflict handling

A conflict is detected when both sides of a mapped field have changed since the last successful sync. The mediator tracks this via `SyncFieldState` (see [data-model.md](data-model.md)) — one row per mapped field pair per linked record (`RecordLink`), storing the last-reconciled baseline **per side** (`lastSyncedHashA`/`lastSyncedHashB`: a transformed field pair holds two representations of one reconciled fact, so each side's baseline lives in that side's own canonical representation and comparisons never cross the transform boundary) **plus the latest value hash observed on each side** (`sideAObservedHash`/`sideBObservedHash`, updated from every webhook, poll result, and write response that touches the field). Critically, `SyncFieldState` is keyed by the *field pairing*, not by a single `SyncRule`: a bidirectional pair (two `SyncRule`s, one per direction) shares the same state, so a conflict is detected correctly regardless of which direction wrote last. When either direction's pipeline is about to write, it checks the *target* side's observed hash against the target side's own baseline — if the target has drifted since the last reconcile, it's a conflict. No extra read of the target is needed; the check runs entirely over observed state.

The honest limit of that approach: the mediator can only compare what it has *observed*. A change on the other side that hasn't been seen yet — made within the current poll interval, say — is detected **late**, when it finally arrives: it then compares against the meanwhile-updated baseline, surfaces as a conflict at that point, and resolves under the same policy. Nothing is silently lost; detection is deferred by at most the observation lag of the slower transport.

That limit is sharpest for a **one-way** rule with no counterpart: nothing routinely observes the target at all — only write responses do — so a manual target-side edit between syncs is not detected *late*, it is not detected, and the next source change overwrites it. One-way sync therefore *means* source-of-truth semantics for the mapped fields, and the enablement UI says so explicitly. Where that is unacceptable, `SyncRule.targetDriftCheck = read-before-write` (see [data-model.md](data-model.md)) trades one extra read per write for drift detection, turning the silent overwrite into a normal conflict.

- **Default policy: last-write-wins by source timestamp — only when both apps declare `capabilities.supportsChangeTimestamps`** (see [data-model.md](data-model.md)). The side with the more recent change timestamp/version wins. This relies on the two apps' reported timestamps being meaningfully comparable, which cannot be assumed across independently-operated external systems with unsynchronized clocks. To keep this from silently picking the wrong side on clock skew: if the two candidate timestamps are within a configurable epsilon (e.g. a few seconds) of each other, timestamp comparison is treated as inconclusive and the mediator falls back to the order in which it *observed* the two changes (webhook arrival / poll detection order) as the tiebreaker, rather than trusting sub-epsilon timestamp differences from two unrelated clocks. When either app does *not* declare change timestamps, timestamp comparison is skipped entirely and observation order is the policy. Either way, the event is still recorded with `SyncEvent.status = conflict` in the Audit Log, so nothing is silently lost from the record even though it's auto-resolved.
- A `FieldMapping` can set its `conflictPolicy` field to `manual-resolve` (see [data-model.md](data-model.md) — this is a sibling field to `transformConfig`, not a value inside it) to override this default and force the conflict to surface in the UI instead of auto-resolving — useful for fields where auto-resolution would be unacceptable. Since `conflictPolicy` lives on `FieldMapping`, it's only meaningful for `FieldMapping`s that belong to a peer-peer `ApprovedMapping`; it has no effect on consumer-provider `FieldMapping`s, which the Adapter Engine never reconciles against a prior state.

**Write granularity under a partial conflict.** When one field of a record is parked for manual resolution, the rest of the record still syncs — the write proceeds with the conflicted field withheld. Withholding is trivial when the target's `update` operation takes partial payloads (PATCH-shaped IR); against a full-replace (PUT-shaped) operation, the executor first reads the target record and carries the target's *current* value through for the withheld field, preserving it rather than overwriting it with the contested source value. The parked field stays flagged until a human resolves it; the resolution then flows through the normal pipeline.

## Ordering and consistency

Sync is asynchronous and eventually consistent:

- **Per-record ordering is guaranteed.** A per-`(mapping, resourceId)` sequential queue ensures two updates to the same record are applied in the order they occurred.
- **Cross-record/cross-mapping ordering is not guaranteed and not required.** Different resources or different mappings may be processed out of order relative to each other.

## Observability hooks

Sync success/failure/skipped-loop/skipped-policy/conflict rates, webhook delivery latency, poller lag (time since `lastRunAt` vs. expected interval), initial-backfill progress/duration, and identity-resolution failures (no-match and ambiguous-match rates) are emitted per `SyncRule` as OpenTelemetry metrics; each individual sync execution is a trace correlated to its `SyncEvent` via `traceId`/`spanId`. See [observability.md](observability.md).
