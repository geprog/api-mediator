# Sync Engine

The Sync Engine executes `ApprovedMapping`s between two `PROVIDER`-role apps on an ongoing basis, keeping their data in sync. It is one of the two consumers of approved mapping data (the other being the [Adapter/Gateway Engine](adapter-engine.md)) — where the adapter resolves requests on demand, the Sync Engine pushes proactively.

## Change detection: polling pull

Each `SyncRule` (one per mapped resource pair of an `ApprovedMapping` between two peer apps, see [data-model.md](data-model.md)) detects changes by **polling** its source app: the Poller periodically calls the source on `SyncRule.pollIntervalOverride` or `RegisteredApp.defaultPollInterval`, using a delta query where the source declares `capabilities.supportsDeltaQuery` and full-fetch diffing otherwise. Polling is deliberately the *only* change-detection transport in this version — one mechanism, uniformly applied, whose staleness bound (the poll interval) is explicit and monitorable (see [observability.md](observability.md)). An app that can be neither listed nor delta-queried (no `supportsPolling`) cannot act as a sync source, though it can still be a sync target or an adapter backend (see [data-model.md](data-model.md)).

Every detected change funnels into the same shared pipeline: **Identity Resolution → Loop Prevention → Conflict Detection → Transformation Executor → Outbound Call Executor**. Identity Resolution runs first because everything downstream operates on the record's `RecordLink` — the echo check compares against link-scoped `SyncFieldState` — so only the short-TTL recently-written cache, keyed by native id, can short-circuit ahead of it (see *Loop prevention* below).

## Polling pull pipeline

1. Scheduler wakes a `SyncRule` on its configured interval.
2. Poller calls the source operation pinned by `SyncRule.pollOperationRef` (see [data-model.md](data-model.md)): the delta-query operation with the stored `cursor` (passed via the resource's confirmed `ResourceBinding.deltaCursorRef`) when the app declares `capabilities.supportsDeltaQuery`, otherwise the collection read — paged to exhaustion via the resource's confirmed `ResourceBinding.paginationRef` — diffing the result against the last-seen snapshot by content hash, keyed by the record's native id (`ResourceBinding.nativeIdRef`). Deletions are only ever inferred from a **complete** full fetch — if any page fails, the run aborts rather than misreading missing records as deletions (see *Change types* below).
3. Each changed record goes through the shared Identity Resolution → Loop Prevention → Conflict Detection → Transformation → Outbound Call pipeline, serialized on the record's cross-direction queue (see *Ordering and consistency* below); an outbound write updates the "recently written by mediator" cache for the target's resource (see *Loop prevention* below), and for a create the target's newly assigned native id is captured from the response (via the target resource's `ResourceBinding.nativeIdRef`) and persisted on the `RecordLink`.
4. `SyncRule.cursor` and `lastRunAt` are advanced; a `SyncEvent` is recorded per changed record.

Full step-by-step walkthrough with sequence diagram: [flows/sync-polling-pull.md](../flows/sync-polling-pull.md).

## Identity correlation: RecordLink

Two independently-owned apps assign their own primary ids to the same logical record — nothing guarantees `customer 123` in App A is `cust_9f3` in App B. Every stateful sync behavior (routing an update to the right target record, conflict detection, delete propagation) therefore runs over an explicit, persisted id pairing: the `RecordLink` (see [data-model.md](data-model.md)), scoped to the unordered app pair and shared by both directions of a bidirectional pair, exactly like `SyncFieldState` (which is keyed by it).

A link is established one of three ways:

1. **Create propagation** — the pipeline creates the record in the target and captures the target's newly assigned native id from the create response, writing the `RecordLink` in the same step. This is also what makes the target's own "new record" event recognizable as an echo (see loop prevention below).
2. **Identity-key match** — during initial backfill, or in steady state when a change arrives for a source record with no link yet: the target is looked up by the mapping's confirmed identity `FieldMapping` (`isIdentityKey`, see [data-model.md](data-model.md)) — the business-level key (email, SKU, order number, …) whose values are expected to identify the same record on both sides. A lookup that matches **more than one** target record never picks one silently: the event is recorded as `failure` with the candidate ids in `details` and surfaced for manual linking.
3. **Manual** — the UI supports explicit linking/unlinking for records an identity key cannot disambiguate.

**How an identity-key lookup executes.** Matching needs the *target* queryable by the identity field's value — which not every REST API offers, so the mechanism is confirmed per resource pair rather than assumed. Preferred: a **filtered read** — the confirmed filter parameter on the target's collection read operation (`FieldMapping.targetLookupParamRef`, suggested by the Mapping Engine and reviewed alongside the identity key itself, see [data-model.md](data-model.md)). Fallback: **fetch-and-match** — a complete fetch of the target resource with in-memory comparison, available only when the target is enumerable (the same complete-fetch capability polling and backfill rely on). A resource pair with *neither* path cannot match records at all: its backfill can only be explicitly skipped, match-first is unavailable (creates go straight to create, risking duplicates for pre-existing data), and links can only be established by create-propagation or manually — the enablement UI states exactly this degradation before the rule can be turned on.

Because a wrong identity key makes the engine silently merge unrelated records — its worst possible failure mode — the identity `FieldMapping` is proposed by the Mapping Engine (`identityCandidate`, see [mapping-engine.md](mapping-engine.md)) but only ever set by explicit reviewer confirmation, and a `SyncRule` cannot be enabled without exactly one confirmed identity key per mapped resource pair (see [flows/mapping-review-and-approval.md](../flows/mapping-review-and-approval.md)).

## Change types: create, update, delete

A detected change carries an action, and "calls the mapped operation" always means *the target operation whose `OperationMapping.action` matches that action* (see [data-model.md](data-model.md)). How the Poller classifies what it detects:

- **Create vs. update** — inferred from snapshot and `RecordLink` state: a record new to the snapshot (or newly reported by a delta query) with no link and no identity match is a create; a record whose content hash changed, or one with an existing link, is an update.
- **Delete via delta query** — only when the API explicitly reports deleted records; a delta API that doesn't report deletions cannot drive delete detection on its own.
- **Delete via full-fetch diff** — a record present in the last snapshot but absent from a **complete** fetch is a delete candidate. This inference is only valid when every page of the fetch succeeded; a truncated or partially failed fetch aborts the run rather than misreading missing pages as mass deletion.

Per action:

- **Create** — before creating, the pipeline first attempts an identity-key match: the record may already exist in the target, created there independently or predating the sync. A match links the records and downgrades the change to an update; no match calls the `action = create` operation, captures the new target id from the response, and writes the `RecordLink`. Create propagation requires an approved `action = create` `OperationMapping` on the target side; a rule without one records observed creates as `skipped-policy` — visible, never silent — the same opt-in shape as delete propagation below.
- **Update** — routed to the target record by filling the target operation's confirmed id parameter (`OperationMapping.targetIdParamRef`, see [data-model.md](data-model.md)) with the `RecordLink`'s target-side native id; a record with no link takes the same match-first path as a create.
- **Delete** — governed by `SyncRule.deletePropagation`, default `ignore`: deletion is the one destructive thing the mediator can do to an app, so propagation is opt-in per rule. Under `propagate`, the `action = delete` operation is called via the link, and the `RecordLink` is **tombstoned** (not deleted) with reason `propagated-delete`: the tombstone is what recognizes the other side's delete echo and prevents a slower poll cycle from resurrecting the record (see loop prevention below). Under `ignore`, the deletion is recorded as `SyncEvent.status = skipped-policy` — visible in the audit log and the graph's activity metadata, never silently dropped — **and the link is still tombstoned**, with reason `observed-delete`: one side of the pair no longer exists, so later changes to the surviving record are recorded `skipped-policy` (counterpart deleted) and surfaced, rather than misrouted at a deleted record or misread as needing a re-create. The surviving record stays unmanaged until it is re-linked manually or matched afresh by a genuine re-create on the deleted side, which arrives with a new native id and establishes a fresh link through the normal create path.

## Initial backfill

Enabling a `SyncRule` between two apps that already hold data raises a question steady-state sync never answers: what about the records that exist *now*? Each rule therefore starts with a one-time backfill run — tracked as `SyncRule.backfillStatus`, see [data-model.md](data-model.md) — before its polling goes live. **The enable action is what triggers it**: enabling a rule (which requires the confirmed identity key, the approved target operations, and both sides' confirmed `ResourceBinding` refs — see [data-model.md](data-model.md)) starts the backfill, and the rule's polling begins only once the backfill has completed — or been explicitly skipped as part of that same enable action (`skipped`); skipping is an explicit choice, never a default. This ordering is deliberate: backfill matching needs the confirmed identity key, so it cannot run at rule *creation* (approval time), and polling must not race it.

1. The Poller does a complete fetch of the source's mapped resource (the rule's `pollOperationRef` collection read, paged to exhaustion). Backfill therefore needs an *enumerable source*: for a source whose resource offers no collection read (a delta-query-only API), backfill can only be explicitly `skipped`, and pre-existing overlap links up gradually via steady-state identity matches or manual linking. Matching likewise needs an identity lookup path on the *target* (see *Identity correlation* above); with neither lookup path, backfill can link nothing — the enablement UI says so.
2. Each record is resolved against existing `RecordLink`s, then by identity-key match; matches produce links.
3. What happens beyond linking is `SyncRule.backfillMode`:
   - **`link-only` (default)** — links are written and `SyncFieldState` baselines are seeded — one row per side-field, from each side's own current stored value (see [data-model.md](data-model.md)) — but **nothing is written to either app**. Two sides *agree* when applying the rule's transform to the source value reproduces the target's stored value: agreement is only well-defined in the target's representation, since comparing raw values across a transform is meaningless. Fields whose two sides disagree get no baseline (there is no last-reconciled value to record) and are reported in the backfill summary; the first subsequent change to such a field is a conflict by construction and resolves per the normal conflict policy below.
   - **`push`** — the source is declared the initial source of truth for this direction: mapped field values are pushed to matched target records, and unmatched source records are created in the target — all through the normal pipeline (loop-prevention tagging, idempotency keys, audit). On a bidirectional pair, at most one of the two rules may use `push`; pushing both directions is a contradiction.
4. Backfill executions are ordinary `SyncEvent`s (`type = backfill-run`); the rule's polling does not start until the backfill has completed or been explicitly skipped (see [data-model.md](data-model.md)), so no steady-state detection races it.

The two rules of a bidirectional pair share links and field state, so whichever backfills first does the bulk of the matching. The second direction's backfill still enumerates *its* source's records — records existing only in that app were never seen by the first run — but finds the overlap already linked.

## Loop prevention

Bidirectional sync — two paired one-way `ApprovedMapping`s / `SyncRule`s, see [data-model.md](data-model.md) — creates a real risk: App A changes → synced to App B by the A→B `SyncRule` → App B's own poll detects that change → the B→A `SyncRule` syncs it back to App A → infinite ping-pong.

Prevention mechanism — durable state is authoritative, the cache is only a fast path:

- **Authoritative check (no TTL):** an incoming change from side X is compared field-by-field against **side X's own reconciled baselines** — the per-side-field `SyncFieldState` rows for side X, each in side X's canonical representation (see [data-model.md](data-model.md)). The comparison covers every side-X field participating in *either* direction's mapping — as a transform's primary input, an additional `aggregate`/`expression` input, or an output — which is what keeps it well-defined even when the two directions pair fields asymmetrically or a transform takes several inputs. If every such field matches its row's last-reconciled hash, the change carries nothing the mediator doesn't already know — it is the echo of the mediator's own write (or a no-op) and is recorded as `SyncEvent.status = skipped-loop`. An echo always arrives on the side that was last written, so this comparison is always same-representation — never across a transform. Because this state is durable, echo detection does not depend on any cache lifetime: the written side's next poll may run hours after the mediator's write, and its echo is recognized all the same. (The check needs the record's `RecordLink` — `SyncFieldState` is keyed by it — which is why Identity Resolution runs *before* Loop Prevention in the pipeline; only the cache fast path below runs ahead of it.)
- **Fast path:** a short-TTL "recently written by mediator" cache per `(appId, resourceId)` short-circuits the common case before field-level comparison, and mediator-originated writes are additionally tagged via a passthrough header/field where the target API supports write metadata. Both are optimizations — correctness never depends on the cache TTL or on the target supporting tags.
- **Canonical-form capture:** target apps may normalize written values (trimming, date reformatting, server-side defaults), which would defeat a naive comparison against what the mediator *sent*. The written side's baseline is therefore recorded from the target's **stored representation** — taken from the write response body when the API returns the updated resource (the common REST case), or via a follow-up read of the written record when it doesn't — while the source side's baseline is the observed source value the write was computed from. The echo then matches exactly instead of ping-ponging over formatting differences.

Two cases content matching cannot cover are handled via `RecordLink` state instead:

- **Create echoes** — when the mediator creates a record in the target, the `RecordLink` written at propagation time (carrying the target's new native id) is what identifies the target's subsequent "new record" poll hit as the mediator's own create rather than a genuine new record.
- **Delete echoes** — a deletion has no content to hash; the tombstoned `RecordLink` is the marker. An observed deletion of a record whose link the mediator tombstoned with reason `propagated-delete` is the mediator's own deletion coming back, recorded `skipped-loop` (an `observed-delete` tombstone marks a severed pair instead — no echo is expected, see *Change types* above). Either tombstone also prevents *resurrection*: a slower poll cycle on the other side, still seeing the record in an old snapshot diff, must not re-create what was just deleted.

## Idempotency

Every outbound write carries a deterministic `idempotencyKey` — a hash of the mapping id, the **source record's native id** (not the `RecordLink`: a create has no link until its response is captured, and the source native id is exactly what two deliveries of the same change share), the resulting payload, **and the prior reconciled state the write was computed from** — the target-side `lastSyncedHash`es of the mapped fields at transformation time, or a distinguished *none* marker for a first write that establishes state. Including the prior state is what distinguishes a genuine value revert from a duplicate delivery: in A → X → Y → X, the third write starts from reconciled state Y while the first started from the initial state, so their keys differ — a payload-only key would wrongly deduplicate the revert as a "repeat" of the first write. A true duplicate delivery (an overlapping or re-run poll, re-processing after a crash) has the same payload *and* the same prior state, and is deduplicated.

Before executing, the Outbound Call Executor checks `SyncEvent` history for the key within a **bounded lookback window** (e.g. the last N events per record or a configured retention period — never unbounded history). The key is also passed through to the target API's own idempotency-key mechanism when it has one.

## Write failures: retry and dead-letter

A failed outbound write (5xx, timeout, network error) is retried with exponential backoff inside its per-record ordering queue (see *Ordering and consistency* below), up to a bounded attempt ceiling. At the ceiling the event is **parked**: recorded as `SyncEvent.status = failure` with a dead-letter marker, surfaced in the UI, and alerted (see [observability.md](observability.md)) — and the queue moves on. A permanently failing record must not block other records, nor later changes to the same record.

Skipping ahead is safe because sync is **state-convergent, not event-sourced**: each execution carries the record's current state, so any later successful sync of the same record supersedes the parked failure entirely. Manual replay of a parked event is only needed when no later change comes along; the replay action re-runs the standard pipeline (including loop prevention and conflict detection against current state) rather than blindly re-issuing the stale payload.

## Conflict handling

A conflict is detected when both sides of a mapped field pairing have changed since the last successful sync. The mediator tracks this via `SyncFieldState` (see [data-model.md](data-model.md)) — **one row per mapped field per side** of a linked record (`RecordLink`), each row holding that side's last-reconciled baseline (`lastSyncedHash`, in that side's own canonical representation, so comparisons never cross the transform boundary), the latest value hash observed on that side (`observedHash`, updated from every poll result and write response that touches the field), and the app-reported change timestamp of that observation (`observedChangeTimestamp`, captured via the side's `ResourceBinding.changeTimestampRef`). Critically, the rows are keyed by side and field, not by a single `SyncRule` and not by a field *pairing*: both directions of a bidirectional pair — whose independently reviewed mappings may pair fields asymmetrically or aggregate several inputs into one target — read and write the same per-side rows, so a conflict is detected correctly regardless of which direction wrote last. When either direction's pipeline is about to write a target field, it checks that field's observed hash against the same row's baseline — if the target has drifted since the last reconcile, it's a conflict. No extra read of the target is needed; the check runs entirely over observed state, serialized against the counterpart direction on the record's queue (see *Ordering and consistency* below) so the two directions can never both pass it concurrently.

The honest limit of that approach: the mediator can only compare what it has *observed*. A change on the other side that hasn't been seen yet — made within the current poll interval, say — is detected **late**, when it finally arrives: it then compares against the meanwhile-updated baseline, surfaces as a conflict at that point, and resolves under the same policy. Nothing is silently lost; detection is deferred by at most one poll interval of the drifted side.

That limit is sharpest for a **one-way** rule with no counterpart: nothing routinely observes the target at all — only write responses do — so a manual target-side edit between syncs is not detected *late*, it is not detected, and the next source change overwrites it. One-way sync therefore *means* source-of-truth semantics for the mapped fields, and the enablement UI says so explicitly. Where that is unacceptable, `SyncRule.targetDriftCheck = read-before-write` (see [data-model.md](data-model.md)) trades one extra read per write for drift detection, turning the silent overwrite into a normal conflict.

- **Default policy: last-write-wins by source timestamp — only when both apps declare `capabilities.supportsChangeTimestamps` *and* both resources have a confirmed `ResourceBinding.changeTimestampRef`** (see [data-model.md](data-model.md)). The side with the more recent change timestamp wins — compared entirely from persisted observations: each side's `SyncFieldState.observedChangeTimestamp`, captured from that side's change-timestamp field at observation time. The drifted side's change was, by definition, seen in an *earlier* poll or write response — persisting its timestamp then is what makes the comparison possible at conflict time without re-reading either app. This relies on the two apps' reported timestamps being meaningfully comparable, which cannot be assumed across independently-operated external systems with unsynchronized clocks. To keep this from silently picking the wrong side on clock skew: if the two candidate timestamps are within a configurable epsilon (e.g. a few seconds) of each other, timestamp comparison is treated as inconclusive and the mediator falls back to the order in which it *observed* the two changes (the rows' `observedAt` order) as the tiebreaker, rather than trusting sub-epsilon timestamp differences from two unrelated clocks. When either app does *not* declare change timestamps (or its ref is unconfirmed), timestamp comparison is skipped entirely and observation order is the policy. Either way, the event is still recorded with `SyncEvent.status = conflict` in the Audit Log, so nothing is silently lost from the record even though it's auto-resolved.
- A `FieldMapping` can set its `conflictPolicy` field to `manual-resolve` (see [data-model.md](data-model.md) — this is a sibling field to `transformConfig`, not a value inside it) to override this default and force the conflict to surface in the UI instead of auto-resolving — useful for fields where auto-resolution would be unacceptable. Since `conflictPolicy` lives on `FieldMapping`, it's only meaningful for `FieldMapping`s that belong to a peer-peer `ApprovedMapping`; it has no effect on consumer-provider `FieldMapping`s, which the Adapter Engine never reconciles against a prior state.

**Write granularity under a partial conflict.** When one field of a record is parked for manual resolution, the rest of the record still syncs — the write proceeds with the conflicted field withheld. Withholding is trivial when the target's `update` operation takes partial payloads (PATCH-shaped IR); against a full-replace (PUT-shaped) operation, the executor first reads the target record and carries the target's *current* value through for the withheld field, preserving it rather than overwriting it with the contested source value. The parked field stays flagged until a human resolves it; the resolution then flows through the normal pipeline.

## Ordering and consistency

Sync is asynchronous and eventually consistent:

- **Per-record ordering is guaranteed — across both directions of a pair.** Every pipeline execution for a linked record runs on a sequential queue keyed by the record's `RecordLink` — deliberately *not* per `(mapping, resourceId)`: the two directions of a bidirectional pair are two mappings, and serializing them separately would leave their shared `SyncFieldState`/`RecordLink` state open to a cross-direction race. The failure this keying prevents: both sides of a linked record change within the same poll window, the two directions' pipelines run concurrently, and each performs its conflict check before the other's write and observation have landed — neither sees drift, both write, and the two sides' values are **swapped**, permanently and silently, with each subsequent echo self-consistently skipped against the updated baselines. Serialized on one queue, whichever direction runs second sees the first's updated state and correctly surfaces the conflict. For a record with no link yet, the queue key falls back to the record's identity-key value — the one value both sides share before a link exists — so two directions concurrently establishing "the same" record serialize too, instead of racing identity-match-then-create into duplicate records.
- **Cross-record/cross-mapping ordering is not guaranteed and not required.** Different records, different resources, or unrelated mappings may be processed out of order relative to each other.

## Observability hooks

Sync success/failure/skipped-loop/skipped-policy/conflict rates, poller lag (time since `lastRunAt` vs. expected interval), initial-backfill progress/duration, and identity-resolution failures (no-match and ambiguous-match rates) are emitted per `SyncRule` as OpenTelemetry metrics; each individual sync execution is a trace correlated to its `SyncEvent` via `traceId`/`spanId`. See [observability.md](observability.md).
