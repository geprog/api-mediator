# Test scenario landscapes

Reproducible docker-compose landscapes of real self-hosted apps, built to
evaluate the api-mediator concept (and later its implementation): the mediator
ingests the **vendored OpenAPI specs** to detect mappings, and the **running
containers** exist so sync (polling) and adapter flows can later be exercised
against live APIs. Every scenario ships a machine-readable ground truth of the
mappings a correct detection run should — and should not — find.

## Scenarios

| # | Directory | Landscape | Focus |
|---|---|---|---|
| 1 | [scenario-1-small-overlap](scenario-1-small-overlap/) | Gitea + Vikunja | 2 peers, small genuine overlap (issues↔tasks, labels, users) → shortlist precision |
| 2 | [scenario-2-multi-overlap](scenario-2-multi-overlap/) | Gitea + Vikunja + Wekan(+Mongo) + Keycloak | 4 apps / 4 domains; overlap web incl. users-only pairs, kanban-state semantics, loop-prevention triangle |
| 3 | [scenario-3-consumer-provider](scenario-3-consumer-provider/) | Vikunja + `todo-widget` CONSUMER spec | minimal adapter case: request/response phases, ParameterMappings, request-phase constants |
| 4 | [scenario-4-mixed](scenario-4-mixed/) | Gitea + Forgejo + Vikunja + `task-dashboard` CONSUMER spec | 3 providers also mapped peer-to-peer; collection-union read, single-binding write, fork pair as detection calibration |
| 5 | [scenario-5-business-suite](scenario-5-business-suite/) | Dolibarr + Kimai + OrangeHRM (each +MariaDB) | ERP/time/HR — the concept's own example domain; relation-shaped mappings, response envelopes, auth diversity |

Consumers are **spec files only** (`specs/consumer/*.yaml`): per the concept, a
CONSUMER spec is the API an app *wishes existed* — the mediator hosts it and
never calls the consumer, so there is nothing to containerize. Host ports
`1<scenario>900` are reserved for the mediator's adapter server.

## Prerequisites

docker compose v2, bash, curl, jq, python3 (+PyYAML), node/npx (spec
conversion + validation). Everything else runs in containers.

## Using a scenario

```bash
cd scenario-1-small-overlap
docker compose up -d --wait   # start the landscape
./bootstrap.sh                # admin users + API tokens -> .tokens.env (idempotent)
./seed.sh                     # OPTIONAL, create-only: overlapping fixture data
../shared/build-specs.sh .    # re-vendor specs from the live landscape
```

Seeding is only needed for future sync/adapter testing — detection runs on the
vendored specs alone. Seed scripts are deliberately minimal and create-only:
run them once on a fresh landscape; `docker compose down -v` is the reset.

All scenarios can run **concurrently** — ports follow `1<scenario><app>`:
Gitea `300`, Forgejo `350`, Vikunja `400`, Wekan `500`, Keycloak `600`,
Dolibarr `700`, Kimai `750`, OrangeHRM `800`, mediator `900` (reserved).

## Specs (`<scenario>/specs/`)

- `full/` — as served/generated by the pinned app versions (version in the
  filename). Wekan/Keycloak don't serve their specs: they are vendored from
  published URLs version-matched to the image tags in `.env`. Kimai/OrangeHRM/
  Dolibarr need a session/generation/API-key — see the `fetch-*-spec.sh`
  scripts in scenario 5.
- `trimmed/` — script-generated subsets (path keep-lists + `$ref`-closure
  pruning) that preserve each overlap story at a fraction of the LLM cost, and
  stay **sync-operable** (list/create/update/delete, pagination, timestamps).
- `oas3/` — OAS 3.0 conversions (most apps serve Swagger 2.0); default
  detection input, originals stay canonical.
- `consumer/` — hand-written OAS 3.1 CONSUMER specs (scenarios 3 + 4).

Real-world messiness is part of the fixture: several vendored specs violate
the strict OpenAPI schema, carry duplicate operationIds, or lie about the
implementation (see each scenario's "concept probes") —
`shared/normalize-spec.py` repairs only what would break parsing/$ref
resolution, the mediator has to tolerate the rest.

## Ground truth (`<scenario>/ground-truth.yaml`)

Per scenario: the resource pairs detection SHOULD find (operations per CRUD
action, identity keys, field mappings with expected transform kinds) and
`negatives` it must NOT confidently propose (`ambiguous`, `no-counterpart`,
`incorrect-but-tempting` — each with rationale). This is what detection
quality gets measured against.
`shared/check-ground-truth.py <scenario>` verifies every referenced operation
exists in the vendored specs, so ground truth can't silently drift on an
image bump.

## Verification

```bash
./verify.sh scenario-1-small-overlap   # DESTRUCTIVE: starts from down -v
```

Runs the full cycle per scenario: compose lint → fresh `up --wait` →
bootstrap ×2 (idempotency) → seed → spec pipeline → live-vs-vendored spec
check → ground-truth check → teardown.
